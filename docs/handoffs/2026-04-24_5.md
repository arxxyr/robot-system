## 3. 架构微调（本 session 发生）

### 3.1 iceoryx2 订阅/发布端 factory closure 入参

**原因**：iceoryx2 `ipc::Service` 家族用 `SingleThreaded` arc_sync_policy，
`Iceoryx2Subscriber<T>` / `Iceoryx2Publisher<T>` 因此 **`!Send`**；plan 原稿的
`spawn_ipc_thread(..., node: Arc<Node<IxService>>, ...)` 编译不过（`Arc<Node>`
要求 `Node: Sync`，但 iceoryx2 `Node: Send` only）。

**解决**：`spawn_ipc_thread` / `spawn_pub_thread` 的入参改为 `subscribers_factory:
FnOnce() -> IpcSubscribers + Send + 'static`（publisher 同理），在线程**内部**
构造 subscribers/publishers。`sync_channel::<()>(0)` 阻塞 spawn 到 factory 完成，
保证调用方拿到 handle 时 subscribers/publishers 已 subscribe/open。

同步信号的正确性已被 `ipc_thread` 6 条集成测试反复验证（无此信号时 
`command_plumbing_writes_pod_buffer` 必 timeout）。

### 3.2 `robot-transport::iceoryx2::channel` 改成 `open_or_create_with_attributes`

**原因**：原实现 `create_with_attributes` 遇到已存在 service 直接报错，跨进程
场景（s0_daemon / mock_s1 / robotctl 同 topic）无法工作。

**解决**：改用 `open_or_create_with_attributes(&AttributeVerifier)`，首次调用
create 并写入 `schema_id` / `schema_version` attribute，后续 open 并 verify。
对 `hello_pubsub` 等旧调用者透明。

同时新增：
- `robot_transport::iceoryx2::subscriber::<T>(&node, topic, class)` 单边 helper
- `robot_transport::iceoryx2::publisher::<T>(&node, topic, class)` 单边 helper

### 3.3 `s0_daemon` 启动时 auto-send `Event::Enable`

**原因**：state machine `SAFE → READY` 需要 `Event::Enable`；v0.2 Part 2 没 RPC
发源。plan 的 "3-terminal 闭环 → state 进入 `ENABLED.Active`" 要求无从满足。

**解决**：`s0_daemon` run() 在 spawn 4 线程 + 注册 signal handler 之后，若 
`initial_estop_latched == false`，立即 `event_tx.send(Event::Enable)`。state
machine 随后收到 mock_s1 heartbeat 自动 `READY → ENABLED.Active`。v0.3 上 RPC
Enable 时替换此 shim（加 `--no-auto-enable` 即可关闭）。

## 5. Orin RT baseline 实测（task 22）

硬件：Orin Nano Super，kernel `5.15.185-tegra #1 SMP PREEMPT`（**非 PREEMPT_RT**）
rtprio=99（已配 limits.d）；6 CPU；schedutil governor（动态调频）；**无** 
`isolcpus` 在 `/proc/cmdline`。

### 5.1 实测数据（3 次 60s/30s，`--priority 70 --strict-rt`）

| 配置 | samples | p50 | p99 | p999 | max | 结论 |
|---|---|---|---|---|---|---|
| `--duration 60s`（无 pin） | 2907/3000 | 22.5 µs | 1018.4 µs | 19955.7 µs | 20021.2 µs | **FAIL** |
| `--duration 60s --cpu 4`   | 2881/3000 | 20.5 µs | 5746.7 µs | 6447.1 µs | 6504.4 µs | **FAIL** |
| `--duration 30s --cpu 4`   | 1470/1500 | 21.0 µs | 15237.1 µs | 15491.1 µs | 15499.3 µs | **FAIL** |

样本 ratio 始终 ≥ 96%，publisher/subscriber 没崩；p50 20 µs 表示**稳态 OK**。
但 p99 每次 1–15 ms 级别、max 同量级 —— 典型 **kernel preempt 延迟尾部**。

### 5.2 为什么 fail（系统层瓶颈，不是代码）

- **Kernel 是 PREEMPT 不是 PREEMPT_RT**：高优先级线程仍被不可抢占临界区阻塞，ms 量级 spike 属常态。
- **Governor = schedutil**：动态调频触发时 CPU 会进 deeper C-state，唤醒延迟数百 µs 到数 ms。
- **未配 isolcpus**：CPU 4、5 照常被内核任务 / IRQ 抢占。
- **未禁 C-state**（`/dev/cpu_dma_latency` 存在但未有进程持 0 写入）。

harness、SCHED_FIFO、mlockall、CPU pin 都正常生效（代码层面已验证 `docs/handoffs/2026-04-24_2.md`
cyclictest max 94–127 µs 也是这个内核）。iceoryx2 叠层没额外爆炸 —— plan §"风险" 第 2 条命中。

### 5.3 要 pass 门槛的方案（Step 6.5 或 Step 7+ 做）

按 plan §"风险" 的 mitigation 清单依次做：

1. **`cpufreq governor = performance`**（sudo 即时生效）
2. **`cpu_dma_latency = 0`**（写 `/dev/cpu_dma_latency` 并持有 fd）
3. **`isolcpus=4,5`** + **`irqaffinity=0-3`**（改 bootloader `cmdline`，重启）
4. **`nohz_full=4,5` + `rcu_nocbs=4,5`**（更激进的隔离）
5. **切 PREEMPT_RT 内核**（JetPack 是否提供 RT patch 需查；也可自编译 linux-tegra-rt）

**本 session 阻塞**：所有这些都要 `sudo` 或 root 改 bootloader；Orin 用户没有 
passwordless sudo，无法当场 tune。留给后续 session / Step 7+。

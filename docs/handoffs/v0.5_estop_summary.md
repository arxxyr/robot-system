## 2. 端到端链路（最终形态，route (a)）

```
robotctl/client ──tonic──▶ gateway e_stop handler（12 步精简：validate→auth→
  authz(operator+ Capability::EStop)→fingerprint→idempotency→shutdown gate→
  build_estop_event(reason, stamp, "rpc", latched=false)→forward→oneshot 等 publish）
        │ 专用常驻 estop_pub_io_thread（crossbeam bounded(64)）
        ▼
  estop_pub publish EStopEvent 到 /<robot_id>/events/estop（source_id=98）
        │  Ack.cleared_at_ns = published_at_ns（弱 Ack，D2）
        ▼
s0 ipc_thread poll_estop（**既有链，0 改**）→ ipc_tick emergency drain
  （guards.estop_latched=true + executor.safety_stop）→ state_machine
  (_, EStop)→Safe（Emergency）→ §6.5 save_estop_latch primary-first fsync
        ▼
  rt/serial tick：emergency_action SAFETY_STOP → adapter safety_stop_fast
  （Feetech 真硬件 = broadcast Torque_Enable=0，< 10 ms）
```

- **弱 Ack 诚实语义**（D2）：`Ack.cleared_at_ns = published_at_ns`，**不**证 S0
  已消费 / latch 已 fsync。`RobotState` 无 `estop_latched` 字段 → **latch fsync
  远程不可观测**（CodeMap B2）。远程客户端可观测面 = `GetState` **运行态**
  （`mode=Safe` / `safety_state ∈ {StopCommanded, TorqueOffConfirmed}`）。
- **`EStop RPC` 不是 S0 死亡场景的救命索**（D1 后果 3）：publish 到 topic 不依赖
  订阅者存活 → S0 不在时 RPC 仍 Ack。该场景由硬件 fail-safe 兜底（§6.7 #1）；
  **AC-7（`s0_dead_still_acks`）e2e 锁这个诚实语义**。
- **无单飞 / 无 RR deadline**（D1 后果 2）：重复 EStop 无害（latch 单调 true），
  emergency **绝不**被 "AlreadyInProgress" 拒（与 ClearEStop RR 路由的反直觉点相反）。
- **机制不对称是设计**（D1）：ClearEStop 走 RR 因它是**危险方向**（解锁，需
  TorqueOffConfirmed gate + confirmation + 强 Ack）；EStop 是**安全方向**（上锁，
  无 gate / 无确认 / 任何时刻执行都对）——design §6.6 字面即 route (a)。

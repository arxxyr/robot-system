## 4. 同 session 软件层 task-30 v9 M7 关键修复回顾

3.x 真机验证靠的是 M7 阶段 4-5 + 三个反向锁测的支撑。本 session 落地的安全语义：

### 4.1 per-event guard view（commit `cf38d5d`）

旧实现：`apply_event_guard_side_effect` 在 `ipc_thread::run_loop` channel
drain 阶段批量调，**前到 event 的 plan_transition 看到的 guards 已被同
batch 后到 event 改写**（`[Enable, ClearEStop]` 同 tick 入队让 Enable 因
ClearEStop 提前清 `estop_latched` 而误进 Ready）。

修订：搬到 `ipc_tick` 内每个 event pop 后 apply，再 plan。`guards`
改 `&mut`。锁测 `events_in_same_tick_use_per_event_guard_view` +
SerialRT E2E `test_same_tick_enable_then_clear_estop_via_channel_does_not_misenable`
钉死。

### 4.2 ClearEStop `TorqueOffConfirmed` 守门（commit `cf38d5d`）

`ExecutorCtrlClient::safety_state()` 新方法。`ipc_tick` 处理
`Event::ClearEStop` 时先检查 `executor_ctrl.safety_state() ==
TorqueOffConfirmed`，否则**不**调 `clear_safety_latch`（state 仍 commit 进
Safe，操作员/RPC 看到 wire confirm 后再发 ClearEStop 才能真正解 latch）。
配套 `client.safety_stop()` 同步重置 `safety_state=StopCommanded`，避免
spawn 初值 `TorqueOffConfirmed` 误判。

### 4.3 rt/serial 兜底 `safety_latched.store(true)` 保留 + race 闭合

rt/serial tick 消费 `emergency_action=SAFETY_STOP` 时仍兜底 store latch=true
（防 emergency 由测试 / 其它路径直置 emergency_action 没经 client 的场景）。
race window 由 §4.2 守门补齐：操作员调 ClearEStop 前必须等
`safety_state=TorqueOffConfirmed`，那时 rt/serial 已消费完 emergency_action
+ 兜底 latch.store 已落地，`clear_safety_latch` 不会被覆盖。

### 4.4 EStop 触发即 fsync latch 落盘（commit `dc45652`）

旧实现仅在 `s0_daemon` graceful shutdown 路径写一次 latch 文件；daemon 在
graceful 退出前崩溃会丢 latch → 重启读 false → 自动 `Event::Enable` →
**安全语义破坏**（reviewer 引 `docs/00_design.md` §6.7 不变量 #4 + §1117）。

修订：`IpcThreadConfig::latch_path: Option<PathBuf>`。`ipc_thread` 主循环
每 tick 比较 `prev_estop_latched` vs `guards.estop_latched`，翻转时立即
`save_estop_latch`（双文件 atomic rename + fsync，~ms 级）。覆盖**所有**
EStop 入口（topic / watchdog / external channel / ipc_tick 内 apply），
不依赖事件来源，只看 guards 翻转。锁测
`estop_topic_writes_latch_to_disk_immediately` 钉死"daemon 仍 active 时
latch 文件已 = 1"。**§5/§7 真机两次端到端验证**：robotctl estop 后 200ms
内 daemon active 时 primary+bak 都 = "1"。

### 4.5 latch 目录前置守门（commit `60ba241`）

`s0_daemon` 启动期 `ensure_latch_parent(latch_path)` 调 `create_dir_all`。
失败直接 `Err(1)` 拒启动 —— 把 fail-late 模式（"deploy 时不暴露，EStop
触发才暴露"）搬到 deploy 时就暴露。runbook 同步显式
`sudo install -d -m 0750 /var/lib/robot/<id>/`。

> Orin daemon + mock_s1 + **2 个 robotctl watch 同跑 11 秒**，A/B 各拿

> `mode=Enabled link=Ok out=Active safety=TorqueOn fault=Unknown`

>
> 详 [`2026-04-26_2.md`](2026-04-26_2.md) §2.1 +
> [`2026-04-26_3.md`](2026-04-26_3.md) §2.5 +
> `docs/CHANGELOG.md` 2026-04-26 "runbook §5.1 known-issue 撤销"。
>

**复现**：daemon + 2 个 `robotctl watch`（**没** mock_s1，**没** sudo），

- 跨 service 隔离的 watch（订 unique topic）暂未试

**follow-up**：~~升 iceoryx2 0.9 / 0.10 看是否 fix；或为 watch 用独立 service

### 5.2 sudo ↔ user 模式切换的 ownership 残留

**踩到的具体路径**（同 session 复现）：
1. `sudo daemon` 写 latch 文件 → root owner
2. 后续 `user daemon` `load_estop_latch` 读 → `Permission denied (os error 13)`
   → daemon 直接 fatal 退出
3. 此外 `sudo daemon` 创建的 `/tmp/iceoryx2/nodes/<uuid>/` 是 root
   owner，下次 user mock_s1/robotctl open service →
   `PublishSubscribeOpenError(ServiceInCorruptedState)`

**结论**：**不要**在同一台机器上 sudo / user 混跑 daemon。统一一种模式。
本 session 选**全 user 模式**（`/dev/ttyACM1` group 是 dialout，user 在
dialout 即可不 sudo 开串口；`strict_rt=false` 不需 SCHED_FIFO）。

**workaround**（切换模式时）：
```bash
sudo rm -f <latch_path> <latch_path>.bak                # 清残留 latch
sudo rm -rf /tmp/iceoryx2/nodes/* /tmp/iceoryx2/services/*   # 清 stale service
```

`Device or resource busy`。
**workaround**：baseline → post-shutdown 对比 motor Position；mid-run

## 6. 工程/部署清单

### 6.1 user-mode 推荐拓扑（本 session 实战）

```bash
# 1) 干净环境
sudo systemctl stop xlerobot-coordinator xlerobot-web
sudo rm -rf /tmp/iceoryx2/nodes/* /tmp/iceoryx2/services/*
rm -f <project>/logs/estop_latch_<id>*

# 2) build（无 sccache 时显式跳）
CARGO_BUILD_RUSTC_WRAPPER= cargo build --release \
    -p robot-s0 --no-default-features --features xlerobot-real \
    -p robot-s1 -p robot-cli
CARGO_BUILD_RUSTC_WRAPPER= cargo build --release --example feetech_poke \
    -p robot-adapter-feetech --features real-hw

# 3) 跑（latch 走项目内 logs/）
target/release/s0_daemon \
    --robot-id ... \
    --hardware-id ... \
    --config configs/<>.toml \
    --latch-path logs/estop_latch_<id> \
    --tick-hz 50 ...
```

**user 模式可行的前提**：
- 用户在 `dialout` group（`groups | grep dialout`）
- `strict_rt=false`（默认；不需要 SCHED_FIFO 真 RT 优先级）
- latch 路径在 user 可写目录（项目内 `logs/` 或 `/tmp/` 或 `~/.local/`）

### 6.2 feetech_poke 命令格式（runbook 已修）

实际 CLI 是 **positional**（不是 `--address` / `--motor-id`）：
```bash
target/release/examples/feetech_poke <address> <motor_id> ping
target/release/examples/feetech_poke <address> <motor_id> read <register>
target/release/examples/feetech_poke <address> <motor_id> write <register> <value>
```

### 6.3 motor Torque_Enable 真机基线

bus2 上 dimos service 退出后 6 motor `Torque_Enable=1`（dimos 退出时**不**
broadcast disable，motor 自身保持上次设置）。runbook §3 smoke 期间 daemon 只
`connect()` 不调 `enable(true)/safety_stop`，motor 状态不变。**§5 真机第一次
确认 `safety_stop_fast` 真 broadcast Torque_Enable=0** 后 6 motor 全 0。

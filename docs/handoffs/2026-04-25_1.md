### 3.5 启动不跳 bug 诊断 + 修复（commit 4/5）

初次三端闭环 ±5° 真机跑完，用户观察到瑕疵：**"启动的时候没跳"（smoke 单端）
但 "mock_s1 接管瞬间夹爪从闭合位瞬间张开到一半" = 36° 跳变**。

推断 → 实测 → 真 root cause：

1. **首假设：adapter 层问题** → commit 4 做 `sync_goal_to_present` readback +
   retry 作 defensive fix（写完 Goal 后 sleep 20 ms + sync_read Goal_Position
   验证，不匹配重写最多 3 次）。
2. **真机复测**：从闭合位 `raw=1418` 起 smoke，Present→Goal 写入**一次就
   生效**（readback 无 mismatch 日志），motor **不跳**。但这是 Torque 已 on
   的场景，**上次跳动的场景是 mock_s1 接管** —— 用户澄清：**"一直都没断电，是
   测试夹爪周期张开闭合才出现的"**。
3. **真 root cause**：mock_s1 正弦公式 `amp*sin(phase)`，第一帧 `sin(0)=0 rad
   = raw 2047 = center`，与 motor 当前位置**无关**就是 center。**S1 command
   源逻辑缺陷**，不是 adapter。
4. **commit 5 真 fix**：mock_s1 `--anchor-timeout-ms <MS>` 启动时订阅 S0 state
   topic 读一帧 `positions[0..joints]` 做 bias，正弦公式改 `target[i] = bias[i]
   + amp*sin(phase + i*π/4)`，第一帧 target=bias=当前位置 → motor 不动。

## 5. 关键决策 / 学到的东西

### 5.1 架构层

- **calibration 只读不写 EEPROM**：dimos 侧已一次性写好 Homing_Offset / Min/
  Max_Position_Limit 到 motor EEPROM；robot-system 二次覆盖风险 > 每次冷启动
  写 EEPROM 的便利。`crate::calibration::write_calibration` 这条路保留给未来
  `robotctl calibrate --apply` 工具命令（task 29 不实现）。
- **启动时 follow-current 防飞**：`enable(true)` 1:1 移植 dimos `_manipulator_
  base.py:468-476` 序列（`sync_read Present → sync_write Goal → sleep 50ms →
  Torque_Enable`）。目的是 Torque 接上瞬间 target == current，电机不动，避开
  Goal 还是旧值导致的"飞向 0"风险。真机验证通过。
- **`CtrlLostHold` 恢复语义**：S1 心跳丢失 → S0 state machine 进
  `CtrlLostHold` 子态 → 自动调 `hold_current_position()` → 读当前 Present 写回
  Goal → 电机冻结当前姿态。真机数据 `-0.008 × 12 次` 确认 drift 不发生，goal
  不归零。
- **bring-up 只动末端夹爪**（用户 2026-04-25 指令）：机械臂未装小车 / 无自持
  情况下，动 shoulder_pan 风险过大；动 gripper 最多就是开合一下，无机械风险。
  bus1 `left_arm_gripper` (ID=6) 是第一个上真机的关节。
- **silent clamp vs reject**：1:1 对齐 dimos —— `_manipulator_base.py:422-426`
  用 `clamp_raw(raw, lo, hi)` 静默夹到边界，不 raise。原因：EEPROM `Min/Max_
  Position_Limit` 已是双保险（电机固件硬限），软件 clamp 只是多一层防护。

### 5.2 接口层

## 7.5 经验教训（本 session 关键学习）

### 7.5.1 先假设后诊断的代价

初次观察到"启动跳到一半" → Claude 猜"Torque_Enable=0 时 sync_write Goal_Position
被 motor 固件忽略" → 直接实现 `sync_goal_to_present` readback + retry（commit 4）
→ 真机复测 **readback 路径没触发 retry**（Torque 已 on，sync_write 本来就成功）
→ 用户澄清 **"一直都没断电，是测试夹爪周期张开闭合才出现的"** → 才定位到
mock_s1 第一帧问题。

**教训**：

- 观察到异常现象时，**先做 instrumentation / 读寄存器诊断**，再判断 root cause。
  本 session 有 `feetech_poke` 能直接读 `Present_Position` / `Goal_Position`
  / `Torque_Enable` —— 如果先读"出 bug 瞬间的 Goal 寄存器"，一眼看到 Goal=2047
  不是闭合位对应 raw 就能秒定位到 S1 层问题，不用多花 1 小时写 adapter 兜底。
- "跳到一半 ≈ center = raw 2047" 这条几何线索应该更早触发 "mock_s1 sin(0)=0
  = center" 的反思，而不是往 Torque 状态钻。
- 防御性修复可保留，但要**注释明说它兜的是哪种失效模式，不是当前症状的修复**
  —— commit 4 代码里这么做了，防止后续 reader 误以为"commit 4 修了 commit 5
  解决的同一个 bug"。

### 7.5.2 架构缺口：state_machine ↔ adapter 执行链路

**发现**：S0 的 `state_machine.rs` 定义了 5 主态 + 4 子态 + 12 事件 + 转换表，
但 **rt_thread 只在 spawn 前一次性调 `adapter.enable(true)`**，之后 state
machine 切状态**不驱动 adapter.enable/disable/set_mode**。`ControlMode::Stop`
从 S1 下发到 adapter 后，`write_command` 看到 Stop 直接 `return Ok()`，**Torque
继续 on**。

**后果**：
- 外部工具（robotctl / mock_s1）**无法通过 iceoryx2 command 让 adapter 下使能**。
  这直接影响 bring-up 场景（例如本 session 要把夹爪推到闭合位，不能远程控制
  torque off 让用户手动推）。
- `state=Fault(...)` 时 motor 仍在 Torque on 状态追最后 Goal，不符合 `safety_stop`
  语义。
- `EStop` 事件触发时应该立刻 `adapter.enable(false)`，当前只是让 state 变到
  `Safe`，不动 motor。

**后续做法**（task-30 候选）：在 `rt_thread` / `ipc_thread` 之外加一个
"io_helper thread"（普通优先级，允许阻塞 IO），用 crossbeam_channel 接收
`AdapterReq::{Enable, Disable, SetMode, SafetyStop}` 请求；状态机 transition
时通过 channel 下发。需要设计 adapter 所有权方案（当前完全 move 进 rt_thread
闭包，需要拆分或用 Mutex）。

### 7.5.3 mock_s1 从"发任意命令"到"模拟真实 S1"

mock_s1 原版正弦从 `sin(0) = 0 rad = center` 开始，与 motor 当前位置完全解耦。
**这不是真实 S1 coordinator 的行为** —— 真 S1 会先读 current state 再 plan
trajectory。本次 commit 5 加 anchor 其实是把 mock_s1 拉回更贴近真实 S1 的起步
行为。

**推广**：future mock_* 工具写的时候，**默认行为要接近真实上游组件的行为**，
而不是"只发静态测试数据"；真正的"静态测试"应该作为显式禁用参数（`--anchor-
timeout-ms 0` 这种）。

### 7.5.4 bring-up 轻量诊断工具的价值

`feetech_poke` 这种 one-shot 裸 wire 命令（读/写单寄存器、ping handshake）：

- 比开完整 `s0_daemon` 轻（不需要 state machine + 4 线程 + iceoryx2 topics）
- 比改 `mock_s1` 通用（任意 motor / 任意寄存器）
- 留在 repo 里长期可用 —— 本 session 内多次救场：
  - 读 Present_Position / Goal_Position / Torque_Enable 确认 motor 状态
  - 直接写 Goal_Position 把夹爪推到 range_min（因为 S0 无下使能入口，这是
    "远程控制 motor 位置"的唯一路径）

**推广**：每个 adapter crate 都应该有对应的 `*_poke` example 或 bin，作为
"不用起完整 daemon 就能验证 wire 层"的诊断工具。

### 7.5.5 硬件 bring-up 的"只动最小单元"原则

用户指令 **"只动末端夹爪"**（bring-up config 从 shoulder_pan ID=1 切到 gripper
ID=6）—— 机械臂未装到小车 / 无自持情况下，动 shoulder 风险远高于动 gripper。
**任何首次真机通电 / 新代码路径上真硬件，先选风险最小的 motor**；下使能 /
fail-safe / 大振幅这些都是后续扩展，不在 bring-up 第一击。

## 3. ClearEStop control-plane slice 草案（A1）

> **范围澄清**：A1 不是把完整 `robot-rpc` 网关提前做完。A1 只做
> `ClearEStop` 这一条安全关键 endpoint 的最小控制面闭环：
> `robot-rpc` 最小 endpoint → S0 内部 `Event::ClearEStop` → latch fsync
> 双写 + 内存 guard 更新。`InvokeTask` / `StreamTaskEvents` / S1 task RPC /
> 其它 §5.3 方法都留 Phase B 的 full gateway。
>
> **语义澄清**：安全语义不是"只能被 gRPC 这一种传输协议解除"，而是
> "只能被显式授权、可审计的 `ClearEStop` control action 解除"。RPC /
> Web 管理界面 / 本地维护面板都只是 transport / UI 入口；它们必须落到
> 同一个 `ClearEStop` action，并走同一套 maintainer+ / confirmation /
> idempotency / `TorqueOffConfirmed` / fsync 双写 / audit guard。此解释先
> 登记到 `docs/CHANGELOG.md` 2026-04-26 "v0.3 entry：`ClearEStop RPC`
> 文案的控制动作解释"条目，后续已在 2026-04-27 以
> `docs/00_design.md` §6.6.1 errata 形式回写。

### 3.1 schema（已在 `docs/00_design.md` §5.2 / §5.3 frozen）

`docs/00_design.md` §5.2 已经定义 `ClearEStopCommand` + `ClearEStop`
RPC，这是 v0.3 A1 的最小外部入口。**v0.3 是落地，不是重新设计**；
但 A1 的安全语义抽象为 `ClearEStop` control action，后续 Web / 本地维护
面板也必须复用同一个 action，不得开旁路。

```proto
message CommandMeta {
    string request_id      = 1;   // UUIDv7；correlation / audit only（每次 retry 改变，详 docs/00_design.md §6.6.2）
    string source          = 2;   // "cli.loosqk" / "web.ui"
    AuthContext auth       = 3;   // token / mTLS cert fingerprint
    uint64 timeout_ms      = 4;   // 客户端 monotonic 相对超时
    string idempotency_key = 5;   // 幂等键（跨 retry 稳定）
    bool   dry_run         = 6;
    string audit_reason    = 7;
}

message ClearEStopCommand {
    CommandMeta meta         = 1;
    string      confirmation = 2;   // 人工确认串
}

// `docs/00_design.md` §5.3：
// rpc ClearEStop (ClearEStopCommand) returns (Ack);   // 独立于 ClearError
```

### 3.2 服务器端 guards（实现时硬要求）

按 `docs/00_design.md` §5.4 + §6.6 + §6.7 #3：

1. **auth**：gateway 先把 `AuthContext.token` / 未来 mTLS fingerprint 解析为
   role，再按 RPC 类型 × role 查 `configs/rpc_roles.toml`。
   `ClearEStop` 只允许 `maintainer` / `admin`；`viewer` / `operator`
   直接拒，返 `PermissionDenied`。S0 端不做授权决策。
2. **confirmation 必填**：`confirmation` 字段空字符串 → 返
   `InvalidArgument`，理由 "ClearEStop requires explicit human confirmation
   string"。具体格式要求（如必须含 `request_id` 后缀 / 操作员姓名）
   v0.3 实现时定，本草案不锁。
3. **idempotency**：`meta.idempotency_key` 命中 A1 最小 endpoint 的
   idempotency cache 时复用第一次结果（`cleared_at_ns` / error），**不**
   重复 fsync。cache 只覆盖 `ClearEStop`；完整跨方法 idempotency 框架留
   Phase B 网关扩展。
4. **state-machine guard**（最重要）：only allow when
   `safety_state == TorqueOffConfirmed`。如果 motor torque 还在 on / 没
   confirm，拒绝并返 `FailedPrecondition`，理由 "safety_state must be
   TorqueOffConfirmed before ClearEStop". 这条防 motor 还在转就 clear
   latch 让 daemon 立刻 enable 的 race。
5. **dry_run**：`meta.dry_run = true` 跳过实际 fsync + state mutation，
   只返预计行为（"would clear latch=true → false; safety_state=...
   would re-arm enable path"）。

### 3.3 实施动作（fsync + state-machine 端到端）

> **A1-2 round 2 + A1-3 (1/3a) 落地后修订**（2026-04-27）：reviewer 拍板把
> RPC I/O 跟 action executor 解耦，ClearEStop 走 backup-first `save_estop_latch_clear`，
> 失败/成功 4 个 domain status 通过 `ClearEStopTickOutcome` 抛给 ipc_thread
> 生成 RR response。下方编号顺序保留，但内部组件名以 A1-2 / A1-3 实施版
> 为准——**不**再按"`robot-rpc` 直接转 external event channel /
> `save_estop_latch(path, false)`"等旧措辞实现。

live 成功路径：

1. `robot-rpc` gateway（A1-3 (2/3) 落地）收 `ClearEStopCommand` → guards
   全过（auth / confirmation / idempotency cache）→ iceoryx2 RR client
   send 到 `/<robot_id>/control/clear_estop` topic。
2. S0 端 `rr_server_thread`（A1-3 (1/3c) 落地）做**纯** iceoryx2 RR I/O：
   decode + 容量检查 + 转发到 `ipc_thread` action executor（crossbeam
   channel）；**不**持 action 状态、**不**调 latch / executor / guard。
3. `ipc_thread`（A1-3 (1/3b) 落地）是唯一 action executor：注册 pending
   元数据（`request_id` 做 correlation；**live 单飞**——第二个 live
   直返 `AlreadyInProgress`；总 pending 上限 64），push `Event::ClearEStop`
   进 events queue。idempotency cache 在 gateway 不在 S0。
4. `ipc_tick`（A1-2）按 `docs/00_design.md` §6.6.1 errata 三步硬顺序消费：
   - `TorqueOffConfirmed` gate
   - `save_estop_latch_clear(path)`（**backup-first**；A1-2 round 2 替代
     旧 `save_estop_latch(path, false)`，保证 partial failure 时磁盘
     latch 不动；详 `docs/CHANGELOG.md` 2026-04-27 round 2 登记）
   - `executor_ctrl.clear_safety_latch()`
   - `guards.estop_latched = false`
   - 填 `tick_outcome.clear_estop = Some(ClearEStopTickOutcome::Cleared
     { cleared_at_ns })`
5. `ipc_thread` 拿 `tick_outcome.clear_estop` → 显式 match 4 variant
   （`Cleared` / `StateNotSafe` / `NotTorqueOffConfirmed` / `FsyncFailed`）
   → 生成 RR response domain status → channel 回 `rr_server_thread` →
   iceoryx2 reply 给 gateway → gRPC `Ack`。
6. **Ack 前置条件**：只有 `Cleared` variant 才返 `Ack { request_id,
   cleared_at_ns }`；其它三 variant 返对应 domain status。**reviewer A1-3
   拍板**：S0 返 domain status，gateway **必须显式 match** 到 `tonic::Code`，
   **不**直接 cast。
7. **fail-closed**：失败 variant 全走 A1-2 "任一步失败 → 后续不执行"；
   `save_estop_latch_clear` backup-first 保证 partial failure 时磁盘
   primary 仍 `1\n`，重启 `load_estop_latch` 仍 `latched=true`（§6.7 #4
   不破坏，详 docs/CHANGELOG.md 2026-04-27 round 2 登记）。

dry_run 路径（reviewer A1-3 follow-up 2 拍板：必须进 daemon/S0，不能
gateway 短路）：

- gateway 端做 auth / confirmation / idempotency 预检，但**不**短路；
  必须发 RR 到 S0。
- S0 端 `ipc_thread` RR drain 直接同步调
  `clear_estop_action::evaluate_clear_estop_dry_run`（read-only），**不**
  进 events queue / `ipc_tick`；返 `WouldClear { would_clear_at_ns }` 或
  domain `FailedPrecondition`（`StateNotSafe` / `NotTorqueOffConfirmed`）。
- torque gate 看 `executor_ctrl.safety_state()` 权威，**不**靠
  `guards.estop_latched` 副本绕过（详 A1-3 (1/3a) commit `cd0bb4d`
  锁测 `dry_run_safety_state_not_torque_off_confirmed_returns_not_torque_off_confirmed`）。
- 不动 latch 文件 / executor latch / guard。

audit v0.3 第一版走 `tracing::info!` + journald，字段至少包含

## 4. freeze hook 测试 sketch（A2）

### 4.1 工程目标

钉死 `docs/00_design.md` §6.7 #2 完整真锁定路径：daemon 内某 worker
被冻 → `LivenessObserver.tick` 停滞 → watchdog 不喂 sd_notify(WATCHDOG=1)
→ `WatchdogSec` timeout → systemd `Restart=on-failure` 拉起新 PID。

### 4.2 freeze hook 设计

每个 worker (`ipc_thread` / `rt_thread` / `serial_io_thread` /
`pub_thread` / `io_thread`) 在 tick loop 顶端加 `cfg(test)` 钩子：

```rust
// crates/robot-s0/src/<worker>.rs tick loop:
while !stop.load(Ordering::Acquire) {
    #[cfg(any(test, feature = "test-freeze-hook"))]
    freeze_check(&metrics, clock);

    // ... 正常 tick 逻辑 (read/write/snap)
    metrics.tick_count.fetch_add(1, Ordering::Relaxed);
}

#[cfg(any(test, feature = "test-freeze-hook"))]
fn freeze_check(metrics: &Metrics, clock: &dyn RobotClock) {
    let frozen_until = metrics.freeze_until_ns.load(Ordering::Acquire);
    if frozen_until > 0 {
        // busy-wait 模拟 cap-deadlock；不 sleep 是因为 sleep 会让线程
        // 让出 CPU 让其它 worker 看似活跃，本测试要的是"线程被 hold 住
        // 但 OS 调度仍在跑"语义。
        while clock.now().0 < frozen_until && !stop.load(Ordering::Acquire) {
            std::hint::spin_loop();
        }
    }
}
```

`Metrics` 加 `pub freeze_until_ns: AtomicU64`（cfg(test) gated 或 feature
gated）。**不**在 RT 线程的 hot path 加 alloc / format / 任何 syscall —
只是一次 atomic load + 条件 spin。

### 4.3 控制路径（test-only）

freeze 触发用 v0.3 测试基础设施新加的 binary：

```bash
# 假名 trigger_freeze（具体 CLI v0.3 实现时定）
target/release/trigger_freeze \
    --robot-id <id> --worker ipc_thread --duration-ms 5000
```

实现可以是：
- 一个 test-only iceoryx2 topic `/<r>/test/freeze`（v0.3 新增；v0.4 删）
- daemon 启动期 `#[cfg(any(test, feature = "test-freeze-hook"))]` 时多
  spawn 一个 control thread 监听这个 topic，把 duration 写进对应
  worker `freeze_until_ns`。

或者更简单：让 freeze 通过 `Metrics` 的 `Arc` 直接被测试 driver 拿到，
test driver 跟 daemon 同进程跑（用 `tokio::process` 起 daemon 然后通过
Arc 共享 metrics 控制 freeze）。具体 v0.3 实现时定。

### 4.4 systemd e2e 测试 sketch

新加 binary `crates/robot-tests/src/bin/freeze_systemd_smoke.rs`：

1. 起一个 `cfg-test` build 的 daemon binary（含 freeze hook，编译时开
   `--features test-freeze-hook`）。
2. 写一个 systemd test unit (`/tmp/test-xlerobot-s0-freeze.service`)
   `Type=notify` + `WatchdogSec=2s` + `Restart=on-failure`，ExecStart
   指向 cfg-test build 的 daemon。
3. `systemctl --user start test-xlerobot-s0-freeze` 起 daemon。
4. sleep 3，捕 PID0，确认 active。
5. 通过控制路径（§4.3）冻 `ipc_thread` 5s。
6. 期望事件序列：
   - t≈0: ipc_thread `tick_count` 停滞
   - t≈1s: watchdog 周期到，`prev == now` → 不喂 ping，journal warn
     `"watchdog: worker tick stalled, withholding sd_notify(WATCHDOG=1)"`
   - t≈2s: `WatchdogSec` 真超时 → systemd `SIGABRT` daemon
   - t≈4s: `Restart=on-failure` 拉起新 daemon → 新 PID1
7. 断言：
   - PID0 ≠ PID1（systemd 真重启）
   - journalctl 看到 `withholding sd_notify(WATCHDOG=1)` warn
   - journalctl 看到 unit 第二次 `s0_daemon starting` + `state=Ready`
   - latch 文件保持原值（fsync 行为不被 watchdog kill 干扰）

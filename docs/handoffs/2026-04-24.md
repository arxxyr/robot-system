### 2.3 RT 线程拓扑方案 B（多 bus 场景）★ 架构级决定

**痛点**：`docs/00_design.md` §1.2 写的是单数 `s0_rt_thread`；多 bus 场景（ATOM01 4 × CAN、XLeRobot 2-3 × USB-RS485）没有明确语义。

**触发**：读 `~/repo/robot/atom01_deploy` 上游 C++ 源码后发现 atom01 用 **每 bus 2 个 SCHED_FIFO 80 I/O 线程（RX async + TX cv+lockfree）+ ThreadPool(4) fan-out** 总 13 RT 线程；且 `dm_motor_driver.cpp:135-160` 的 RX callback 里直接 `spdlog::error(...)` format + 写非 atomic `float` 成员，**违反 §4.9 RT 铁律 + 有数据竞态**。

**用户 EtherCAT 背景**：单 RT 线程 `[read → update state queue → read target queue → safety → write bus]` 跑得稳。

**决定**（commit `66519a6`，CHANGELOG 2026-04-24 条 1，状态"登记 / 候选回写 §1.2"）：

1. **每 HardRT bus 一个 rt_thread**，tick 闭环：
   ```
   clock.sleep_until(deadline); deadline += tick_period;
   bus.drain_rx();                            // non-blocking 到 EAGAIN
   cmd = target_slot.load_latest();           // SampleLease latest-wins
   if fault = safety_check(&state, &cmd) { bus.safe_output(); continue; }
   bus.write_frames_serial(&cmd, &state);     // N 次 write()，稳态 <10 µs/次
   snapshot.write_bus_slice(bus.id, &state);  // per-bus seqlock
   ```
2. **不采用** atom01 的 async RX + TX queue 模式（RT-unsafe + 复杂度 8 倍）。
3. **`RtSnapshotWriter` 加 per-bus slice 维度**（seqlock 分片；v0.4 多 bus 首次落地时定形 API，v0.2/v0.3 保持单 slice 等价实现）。
4. **跨 bus compute**（闭链解耦 / IK）不进 rt_thread，挪 `robot-s1` coordinator。
5. **`write()` `EAGAIN` 不 retry**，记 metric + 跳过，恢复上抛 s1 / 业务 app；靠 `SO_SNDBUF ≥ 1 MB` + `txqueuelen ≥ 1000` 保稳态不 block。
6. **v0.2 Step 6 / Step 10 仍 M=1**（单 bus mock、单关节）；真多 bus 在 v0.4 (XLeRobot) / v0.5 (ATOM01) 落地。
7. **候选回写 §1.2 的触发**：XLeRobot v0.4 多 bus + cyclictest 1 h p99 < 1.5 ms + EAGAIN = 0 三项满足后正式回写。

**memory 已存**：`memory/rt_thread_per_bus_topology.md`（feedback 类，跨 session 持久化）。

### 2.4 policy_host 调度在 RT 内核下等价 inline + iceoryx2 RT baseline 提前到 Step 6

**痛点**：评估"能否替代 atom01"时，唯一未 closed 的架构级未知是 policy_host 独立进程 vs inline ONNX 的调度抖动。

**用户澄清**：atom01 运行环境**已经是 5.10 RT（OPi 5+）/ 6.1.83 RT（RDK X5）**，`rtprio 98 + memlock unlimited` 就位。

**决定**（commit `b1e23ee`，CHANGELOG 2026-04-24 条 2，状态"登记 / 验收条件冻结"）：

## 3. ATOM01 替代结论（session 开始 → 结束）

### 初判（session 开始）

架构上能，工程上差 v0.2-v0.5 四个版本，**三个真实不确定点**：policy_host 抖动 / SocketCAN write 阻塞 / 状态残留。

### 收口（session 结束）

**可以替代，而且替代后关键 RT 属性与原栈同级或更好**。

三个不确定点：

| # | 上一轮状态 | 现在状态 | 原因 |
|---|---|---|---|
| policy_host 调度抖动 | 真风险 | **已 closed** | RT 内核在手 + SCHED_FIFO + CPU pin + mlockall |
| SocketCAN write 阻塞 | 真风险 | **已 closed** | 方案 B + SO_SNDBUF + txqueuelen + EAGAIN 不 retry |
| 策略切换 state 残留 | 真风险 | 工程任务 | §2.9 契约冻结清单；engineering 细节，不是架构问题 |

**三个 robot-system 架构级优于 atom01 的点**（都是"天然免疫"原栈的隐疾）：

1. `RobotClock::sleep_until(deadline)` vs 原栈 `sleep_for(period - elapsed)` 会漂移
2. `RtSnapshotWriter` per-bus seqlock vs 原栈 `joint_mutex_` + `motors_mutex_` 全局锁 + ThreadPool barrier
3. §4.9 RT 铁律 + `assert-no-alloc` / `rt_arc_guard` 守卫 vs 原栈 RX callback 里 spdlog format + 非 atomic 共享

**Fault 处理差别**：原栈 motor offline → `std::runtime_error` → `rclcpp::shutdown()` 整栈挂；robot-system → fault code + EStop latch 双 fsync + `CONTROL_LOST_*` 子态切换 + 手动 `ClearError` 恢复。

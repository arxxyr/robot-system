## 1. 结论

当前实现达到的是：

> **左右臂在配置、串口设备、S0 进程和 systemd watchdog 层基本隔离；协议校验、
> 启停保护、错误计数和失败后重启链已经具备，足以支撑人员在场的受监督功能
> demo。它尚未达到逐电机故障隔离、硬实时资源隔离、电机失联自动断扭或无人值守
> 生产级健壮。**

因此不能笼统写成“电机通信已经独立健壮”。准确分级如下：

| 维度 | 当前判定 | 说明 |
|---|---|---|
| 左右臂配置与串口隔离 | 已具备 | 两个独立 by-id 串口、两份 arm-only config、两个 S0 unit |
| 左右臂进程故障域 | 已具备 | 每臂独立 S0/S1/gateway 和独立 systemd watchdog |
| USB 控制器、IRQ、供电故障域 | 未证明 | 不同 by-id 不等于不同 root hub、控制器、IRQ 或电源 |
| 单臂内逐电机故障隔离 | 未具备 | 6 个电机共享一条半双工总线；一个回包异常可使整批读取失败 |
| 通信错误检测 | 已具备 | 包校验、ID/顺序校验、超时和读写错误计数 |
| 通信自动恢复 | 部分具备 | 可由 systemd 重启 S0；缺少连续错误阈值、RX 重同步和串口 reopen 状态机 |
| S0 CPU/调度隔离 | 未具备 | Feetech 走普通优先级 `SerialRT`，生产 unit 未绑定 CPU |
| S0 资源保护/限制 | 仅采样 | CPU/RSS 有监测，无阈值执法、资源预留或 cgroup 隔离 |
| 电机侧 command watchdog | 未具备 | STS3215 无已文档化、可配置的失联断扭 watchdog |
| 跨臂自主安全联锁 | 未具备 | 一臂 S0 自主 Fault 不会在 daemon 层强制另一臂断扭 |

当前唯一允许的收口宣称仍是：**机器人控制执行面受监督功能 demo 跑通**。
`D15` 硬件 fail-safe 保持 OPEN，不得据本文升级为生产替换或无人值守宣称。

## 2. 电机通信独立性

### 2.1 左右臂已经隔离的部分

- 左臂串口固定为
  `/dev/serial/by-id/usb-1a86_USB_Single_Serial_5A7C121427-if00`，右臂固定为
  `/dev/serial/by-id/usb-1a86_USB_Single_Serial_5A7C122340-if00`：
  `configs/xlerobot_left_arm.toml:26`、
  `configs/xlerobot_right_arm.toml:18`。
- 每臂使用独立 `robot_id`、`hardware_id`、latch、S0 unit 和 restart budget：
  `scripts/systemd/xlerobot-s0-left-arm.service`、
  `scripts/systemd/xlerobot-s0-right-arm.service`。
- `deploy::identity` 在打开串口前校验机器人身份、hardware 身份、完整 by-id 路径、
  joints、motor IDs、标定文件和 `auto_enable=false`，防止左右配置互换或串口漂移：
  `crates/robot-s0/src/deploy/identity.rs`。
- 启动/重启前 guard 对本 bus 全量执行断扭写入与 readback；首次 handoff 对全部
  17 个电机执行安全交接。失败时 fail-closed，不进入 `s0_daemon`。

这些措施能够隔离大部分配置错误、进程崩溃和单侧串口打开失败。

### 2.2 尚未证明的物理独立性

两个不同 by-id 设备仍可能共享：

- 同一 USB root hub 或 host controller；
- 同一 IRQ 或内核 USB 工作队列；
- 同一 USB 供电、转接板电源或总电源；
- 同一 CPU 调度和系统内存压力域。

因此段 `(10-demo)` 前必须在 Orin 上保存以下证据，才能判断左右 bus 的实际故障域：

```bash
lsusb -t
udevadm info -q path -n /dev/serial/by-id/usb-1a86_USB_Single_Serial_5A7C121427-if00
udevadm info -q path -n /dev/serial/by-id/usb-1a86_USB_Single_Serial_5A7C122340-if00
cat /proc/interrupts
```

### 2.3 单条 bus 内不是逐电机独立

一条 arm bus 上的 6 个电机共享同一个 `FeetechBus` 和串口：

- `sync_read_by_id_into` 发一次批量读，然后用 `read_exact` 等待全部 status packet；
  任一电机静默、截断、错序或 checksum 错误都会使本轮整批读取失败：
  `crates/robot-adapters/feetech/src/bus.rs:362-403`。
- 正常 `Goal_Position` 使用 broadcast `sync_write`，不等待 ACK；OS 写成功不证明
  每个电机都已消费命令：`bus.rs:406-434`、`adapter.rs:542-581`。
- 紧急断扭为了低延迟同样先发一次无 ACK broadcast；随后由
  `read_torque_enable_mask` 逐项确认并升级为 `TorqueOffConfirmed`、
  `AdapterUncertain` 或 `StopFailed`：`adapter.rs:404-448`、
  `serial_io_thread.rs:374-443`。

这种策略偏向 fail-closed 和一致状态，不提供“坏一个电机，其余五个继续运行”的高可用性。

## 3. 已有的通信健壮性

### 3.1 协议与启动守门

- Feetech 包包含 header、长度、ID、错误码和 checksum 校验：
  `crates/robot-adapters/feetech/src/protocol.rs:264-324`。
- 启动 handshake 会逐个 ping 配置中的电机并校验 STS3215 model；任一缺失或型号
  不符都会拒绝启动：`crates/robot-adapters/feetech/src/bus.rs:90-142`。
- adapter connect 阶段校验 calibration motor ID 与 bus motor ID 一致，避免标定映射错位：
  `crates/robot-adapters/feetech/src/adapter.rs:459-489`。
- enable 前先读取当前位置、把 Goal 设置为 Present、readback 后再逐电机上扭，降低
  启动跳变风险：`adapter.rs:235-330`、`adapter.rs:616-635`。
- `Torque_Enable` 关键写采用逐电机 ACK、最多 3 次重试；单项失败后仍继续处理后续
  电机，最终返回首个失败：`adapter.rs:349-401`。

### 3.2 读失败的事务语义

`serial_io_thread` 先把读取结果写入临时副本，只有读取成功才同时提交状态和采样时间戳；
读取失败时保留 last-known-good 状态与旧时间戳：
`crates/robot-s0/src/serial_io_thread.rs:484-508`。

该语义保证：

- adapter 即使在返回错误前部分改坏输出，也不会污染正式快照；
- 下游仍能根据旧 `stamp_ns` 判定数据 stale；
- 持续串口故障不会被伪装成持续产生新鲜状态。

## 4. 看门狗现状

### 4.1 已具备

| 层级 | 当前机制 | 触发结果 | 边界 |
|---|---|---|---|
| S1 heartbeat | S0 默认 `200ms` 未收到 heartbeat | 进入 control-lost 状态族 | 不是电机失联断扭 watchdog |
| S0 worker liveness | 观察 IPC、executor、pub、IO 四类 tick counter | 任一停滞则停止喂 systemd | 能抓阻塞/死锁，不能抓持续快速返回的错误 |
| S0 systemd | `WatchdogSec=2s` | systemd 重启该侧 S0 | 重启前电机可能持续带扭 |
| S1/gateway systemd | 生产 `WatchdogSec=5s` | systemd 重启对应进程 | 不直接控制电机断扭 |
| 串口单次读取 | 默认 `1000ms` IO timeout | 本轮读取返回错误、错误计数增加 | 只是 IO timeout，不是安全 watchdog |

代码锚点：

- S1 heartbeat 默认值：`crates/robot-s0/src/bin/s0_daemon.rs:161`。
- S0 liveness observer：`s0_daemon.rs:1034-1072`。
- S0 watchdog unit：`scripts/systemd/xlerobot-s0-left-arm.service:86`、右臂同址。
- S1/gateway watchdog：`scripts/systemd/xlerobot-s1-left.service:37`、
  `scripts/systemd/xlerobot-gateway-left.service:43`，右臂同款。
- 串口默认超时：`crates/robot-adapters/feetech/src/registers.rs:42-43`。

### 4.2 明确缺失

1. **没有电机侧 command watchdog。** STS3215 没有已文档化、可配置的“通信失联后
   自动断扭”寄存器；当前真机行为证据是 hold-last-position 且持续带扭。
2. **没有连续通信错误 watchdog。** `read_errors`/`write_errors` 当前只是计数；若串口
   每轮快速返回错误但线程继续递增 tick counter，systemd watchdog 不会触发。
3. **没有完整的串口恢复状态机。** 运行路径使用固定长度 `read_exact` 和直接解析，尚未
   落地超时后的 RX drain/header 重同步、端口 reopen、连续失败阈值与升级语义。
4. **没有 `<500ms` 的 S0-dead fail-safe。** S0 死亡后要等待 systemd 检测、重启和 guard
   preflight；该窗口内电机可能保持带扭。`D15`/`AC-E25` 因此保持 OPEN。

## 5. S0 实时性、CPU 绑定与资源分配

### 5.1 当前 Feetech 路径不是 HardRT

仓库具备 HardRT 线程能力：`SCHED_FIFO 70`、`mlockall` 和可选 `--cpu` 绑核，见
`crates/robot-s0/src/rt_thread.rs:240-253`、`518-548`。

但这套能力**不用于当前 Feetech 电机通信**：

- Feetech factory 明确实现为 `RtClass::SerialRT`：
  `crates/robot-adapters/feetech/src/factory.rs:168-176`。
- `SerialRT` 运行在普通优先级 `serial_io_thread`，允许串口 IO 毫秒级阻塞，不走
  `SCHED_FIFO`、`mlockall` 或 `--cpu`：
  `crates/robot-s0/src/serial_io_thread.rs:198-224`、
  `crates/robot-s0/src/bin/s0_daemon.rs:815-833`。
- 生产 arm unit 没传 `--cpu`，没有 `CPUAffinity`/`AllowedCPUs`，并设置
  `RestrictRealtime=yes`：`scripts/systemd/xlerobot-s0-left-arm.service:70-112`。

因此当前只能宣称“SerialRT 普通线程 + systemd liveness”，不能宣称已绑定专核或达到
硬实时调度保证。

### 5.2 当前资源策略

- `robot-health` 每秒采样 S0/S1/gateway CPU 和 RSS：
  `configs/xlerobot_left_arm.toml:50-52`，右臂同款。
- 当前没有 CPU/RSS 阈值执法，也没有 `CPUQuota`、`MemoryMax`、`CPUWeight`、
  `MemoryMin`、`OOMScoreAdjust` 或独立 cpuset。
- 暂不直接加 `CPUQuota`/`MemoryMax` 是合理的：CPU throttling 或 OOM kill 可能主动杀死
  安全进程。资源策略应优先保护 S0，而不是在没有基线时硬限制 S0。

### 5.3 推荐的资源隔离方向

1. 先在 Orin 采集真实 topology、IRQ、CPU/RSS、串口 RTT 和调度延迟，不预钉 CPU 编号。
2. 左右 S0 使用不同 CPU 集；不要把整个 S0 所有线程绑到单核。每侧至少区分：
   - SerialRT/USB IRQ 工作资源；
   - IPC、发布、watchdog 等 housekeeping 资源。
3. 不应直接把 USB 串口线程提升为 `SCHED_FIFO 70`。USB-RS485 本身不是硬实时链路；
   应先证明最大 RTT、阻塞上限和内核 IRQ 行为，再决定普通优先级绑核、`SCHED_RR` 或
   其他调度策略。
4. 资源保护优先评估 `CPUWeight`、`MemoryMin`、`OOMScoreAdjust` 和独立 systemd slice；
   `CPUQuota`/`MemoryMax` 只有在有峰值数据、OOM/节流验证和回滚方案后才能拍板。
5. 若未来启用真正 HardRT adapter，必须同步审查 `RestrictRealtime`、`LimitRTPRIO`、
   `LimitMEMLOCK`、capability、CPU affinity 和 IRQ affinity，不能只在 CLI 增加 `--cpu`。

## 6. 建议优先级

### 6.1 段 `(10-demo)` 前必须记录，但不要求本轮改生产代码

- 核实左右 USB 拓扑、控制器、IRQ 和供电故障域；
- 记录每个 S0 的 MainPID、线程 CPU 落点、调度类和实时优先级；
- 按既有 Plan 采集每进程至少 30 帧 CPU/RSS，并记录 synthetic transport latency；
- 保持 `auto_enable=false`、机械隔离、人员在场和可立即切总电源；
- Enabled 期间任一 S0 死亡或重启，立即人工断总电源并中止本轮。

建议记录命令：

```bash
systemctl show xlerobot-s0-left-arm.service \
  -p MainPID -p AllowedCPUs -p CPUAffinity -p CPUWeight \
  -p MemoryCurrent -p MemoryMin -p MemoryMax -p OOMScoreAdjust
ps -L -p "$(systemctl show -p MainPID --value xlerobot-s0-left-arm.service)" \
  -o pid,tid,psr,cls,rtprio,pri,ni,comm
```

右臂执行同款命令并保存对照。

### 6.2 post-E 生产安全硬化

按风险排序：

1. **P0：闭合 D15。** 在硬件断电 watchdog、继电器或独立监督器中拍定并实现一种，
   使 S0-dead 后 `<500ms` 可证明进入安全态。
2. **P0：补通信故障升级链。** 为连续读写错误定义阈值、Fault/断扭语义、RX 重同步和
   有界串口 reopen；错误快速返回时也必须触发，而不能只依赖 systemd liveness。
3. **P1：完成 CPU/IRQ/cgroup 隔离。** 基于 Orin 实测拓扑为左右 S0 分配独立资源域，
   并加入可复跑的调度与资源证据。
4. **P1：补跨臂 daemon-independent 联锁。** 一侧自主 Fault/EStop 时，另一侧不得依赖
   上层 client 仍存活才进入安全态。
5. **P2：评估逐电机降级。** 明确单电机失联时是整臂 fail-closed，还是支持隔离坏电机；
   在安全语义拍板前不得擅自让其余电机继续执行。

## 7. 最终判定

- **可以做：** 受监督、机械隔离、操作者可立即断电的段 `(10-demo)`。
- **不可以宣称：** 逐电机独立、USB 物理故障域独立、硬实时、S0-dead 自动断扭、
  无人值守双臂运行或正式生产替换。
- **看门狗准确口径：** 软件进程与 S1 heartbeat watchdog 已有；电机侧失联安全
  watchdog 和连续通信错误升级 watchdog 仍缺失。

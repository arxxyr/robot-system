## 2. 第一个 backend 选什么（**待拍板 #1**）

四选一，按工程难度递增：

### 2.1 选项 A — `HoldPose`（推荐 / 用户倾向）

**行为**：复用 B1 `build_hold_command`，每 tick 产 `target = anchor_bias`
的 `JointCommand` body bytes。等价 Idle 状态的 hold loop，但走 EXECUTING
路径。

**优点**：
- **复用 B1 builder**，零 motion 风险；新代码量最小。
- 验证 B2 action path 不仅服务 mock_dwell（mock_dwell 返 None；
  HoldPose 会真返 Some(body)，激活 override 的 publish 分支，跟 B2
  (3/3) `happy_b` 测试同款路径但用真 backend）。
- 不需扩 `ActionKind` enum（B2 已声明 `HoldPose` variant 但没 backend
  实现；B3 补 backend 实现即可）。
- 不需 payload schema（payload 为空，`supported_schemas() =
  &[NO_PAYLOAD_SCHEMA_ID]`）。

**缺点**：
- 行为简单，不验证更复杂 backend 的边界（payload 解码 / 多关节
  trajectory 插值 / IK 反算）。后续 B3+ / v0.4 真 backend 时还需
  Scripted / Trajectory 的更高 churn。

**剩余设计点**（如选 A，**待拍板 #2**：duration 语义）：
1. **完成条件**：
   - **(a)** `HoldPose` 长 dwell 持续到 cancel —— B2 outline §2.2
     "等价 IDLE 但走 EXECUTING 状态路径"语义最自然；只能 cancel 退出。
   - **(b)** `HoldPose { duration_ms }` 字段 —— 跟 mock_dwell 同款，
     dwell N ms 后 `Completed(Success)`。
   - **(c)** dwell 到 `ActionRequest.deadline_ns` —— 复用 B2 字段，
     不引新参数；但 deadline 语义本是"超时即 fail"，借作"完成时点"
     会让真 backend 实现混淆（同 B2 mock_dwell 拍板时已避开此选项）。
2. **default duration**（如选 (b)）：100 ms？1000 ms？永不完成（只能
   cancel）？

   **默认推进**：**选 (a) hold-until-cancel** —— 跟 B2 outline §2.2
   "等价 IDLE 但走 EXECUTING 路径"语义对齐，最简单；如要 fixed
   duration 留 B3+ 扩字段。

3. **anchor_bias 来源**：每 tick 读 `ActionContext.anchor_bias` —— B2
   ActionContext 已暴露 `&[f64]`，跟 Idle hold 用同一份 anchor。
   **不**在 backend 内部 capture snapshot（避免跟 coordinator anchor
   不一致；B3 期间 anchor_bias 构造期固化不变，capture 与否等价；保
   留每 tick 读为 v0.4 扩动态 anchor 留扩展点）。

4. **`source_task_id`**（**reviewer round 2 阻断 1 拍板**）：HoldPose body
   里的 `source_task_id` **必须**等于 `run_action_tick_loop` 当前
   `TickState.cmd_seq`，**不**得 backend 自己从 0 计数。

   **理由**（round 1 私有 counter 默认推进被打回）：
   - `crates/robot-s0/src/ipc_thread.rs:903` 把 `fb.source_task_id()` 直接
     写成 `JointCommandBuf.seq`（**不**是 `FrameHeader.seq`）。
   - `crates/robot-core/src/adapter.rs:119-120` 注释要求 `seq` "命令 seq
     号，单调递增；rt_thread 判 CONTROL_LOST → ACTIVE 恢复时用"。
   - 如果 backend 私有 counter 从 0 起：daemon 先 Idle hold 跑 N 帧
     （source_task_id = 0..N），进入 EXECUTING（HoldPose 私有 counter =
     0..M），S0 看到 seq 序列 ..., N, **0**（回退）→ 破坏 adapter 单调
     契约，可能误触 `CONTROL_LOST` 恢复路径。
   - 不仅是 audit 字段问题，是 wire 协议契约。

   **实现路径**（reviewer round 2 显式放行 B3 做最小 lib API 调整）：
   - **(i)** `crates/robot-s1/src/action.rs::ActionContext` 加字段
     `pub command_seq: u64`（B2 round 1 reviewer 锁定的 ActionContext 字
     段集 round 2 解除"仅本字段"，详 §3.4）。
   - **(ii)** `crates/robot-s1/src/coordinator.rs::Coordinator::tick_action`
     签名加 `command_seq: u64` 参数：
     ```rust
     pub fn tick_action(&self, clock: &dyn RobotClock, command_seq: u64)
         -> Option<JointCommandBody>;
     ```
   - **(iii)** `run_action_tick_loop` 调 `coordinator.tick_action(clock,
     state.cmd_seq)` 传入当前 publish frame 的 cmd_seq；backend
     `tick(ctx)` 内 `ctx.command_seq` 就是即将 publish 的 frame seq。
   - **(iv)** HoldPose backend 内部 `build_hold_command(cfg, layout_id,
     anchor_bias, ctx.command_seq, ctx.clock.now().0)` 直接复用即可。

   **影响面**：所有 `ActionContext` 构造点需补 `command_seq` 字段（lib
   测试 / mock_dwell 测试 / `tests/action_dispatch.rs` / `coordinator.rs`
   测试 ScriptedSomeBackend / SafetyAbortBackend 等）。补 `command_seq:
   0` 即可，因为这些测试 mock 路径不参与真 wire publish 单调性验证。
   不动 `ActionInstance::tick` / `ActionBackend::start` trait signature
   （它们仍用 `&mut ActionContext`）。

   **拒方案**：
   - **(a)** ~~backend 内部私有 counter 从 0 起增~~ —— 破坏 wire 契约
     （round 1 默认推进，round 2 阻断 1 打回）。
   - **(b)** ~~总用 0 / action_id 哈希~~ —— 同样破坏单调契约。
   - **(c)** ~~Coordinator 自管 cmd_seq 不传给 backend~~ —— 那 backend
     就没办法用 `build_hold_command(..., source_task_id, ...)` 构造正确
     bytes；只能 coordinator 重新 wrap body 替换 source_task_id 字段，
     fbs 字段重写昂贵（rebuild 整个 buffer），不如 (i)+(ii)+(iii) 干净。

   **取代默认推进**：**(i)+(ii)+(iii)+(iv) 锁定**。tick_action 签名变更
   是 B3 (1/2) commit 公开 API 改动，**不**算"既有 API 语义改"（B2
   `tick_action` 才 land 一周；B3 round 2 reviewer 显式拍板放行，跟 B2
   reviewer 拍板"如确实需要扩 lib 类型"同款放行模式）。

### 2.2 选项 B — `Scripted`

**行为**：读 TOML / 内嵌字面量描述的 (t_ms, joint_targets) 时间序列，
backend tick 按时间步进，到帧产对应 `JointCommand` body bytes。

**优点**：
- 比 HoldPose 更接近实际任务（多帧 cmd / target 真变化）。
- 验证 backend tick 跟 50 Hz cmd_period 协作（每 tick 选下一帧 vs 插
  值）。

**缺点**：
- 需要 payload 方案（脚本怎么传？inline TOML / `payload: Vec<u8>` 编
  码 frames / payload_schema_id 方案）—— 跟 B2 outline §10 决策 #9
  "payload schema 推到 B4"冲突。
- 需扩 `ActionKind::Scripted` variant + 新 schema_id 常量。
- 多关节插值 / 速度限幅 / safety check 等 B3 是否做？做多深？容易
  scope creep。

### 2.3 选项 C — `Trajectory`

类似 Scripted 但更结构化（pose 序列 + 时长 + 插值算法）；scope 更
大；不适合"第一个真 backend"。

### 2.4 选项 D — `IK / RL`

需要 `robot-kinematics` crate（设计文档列出但 v0.4+ 才引入）/ `ort`
ONNX runtime；超出 B3 边界，留 v0.4。

### 5.2 in-process 集成测（`tests/action_dispatch.rs` 扩条目）

补 2 条（reviewer round 2 收紧 ground truth 断言形态）：

- `happy_hold_pose_publishes_hold_cmd_bit_equivalent_through_override`：
  submit HoldPose → `run_action_tick_loop` 100ms → 验：
  1. cmd_ch.publishes() ≥ 4（override 路径下 backend Some(body) 真
     publish）。
  2. **bit-equivalent 收紧版**：`cmd_ch.subscriber().latest()` 取最新
     publish body bytes；用 fbs 解码读 `body.source_task_id()` +
     `body.deadline_ns()` 反推 `now_ns = deadline_ns -
     cfg.deadline_offset_ns()`；用 `build_hold_command(cfg,
     layout_id, anchor_bias, source_task_id, now_ns)` 构造 ground
     truth；`assert_eq!(body, ground_truth)` 字节级相等。
  3. **monotonicity 跨段验证**：cmd_ch 历次 publish 的 `source_task_id`

### 1.1 在范围

  `ClearError` = **共 5 个 method** 默认推进，详 §3 待拍板 #2）：

## 3. RPC method 选择（**待拍板 #2**）

### 3.1 默认推进 5 个

| RPC | 来源 | 用途 |
|---|---|---|
| `InvokeTask` | design §5.3 | 提交 action → 返 `TaskHandle = ActionId` |
| `CancelTask` | design §5.3 | 取消 action |
| `GetTaskStatus` | design §5.3 | 查询单个 action 当前状态 |
| `StreamTaskEvents` | design §5.3 | 订阅 action 事件流（server streaming） |
| `ClearError` | design §5.3 | 清 coordinator `Degraded` 状态 |

理由：
- 这 5 个直接对应 B2 (2/3) `Coordinator::{submit, cancel, status,
  clear_error}` 4 API + B2 (1/3) `ActionTicket.events` 接口。lib
  side **已埋好**接口；B4 仅做 RPC wiring。
- `ClearEStop`（A1）+ 这 5 个 = `RobotControl` service 的所有控制
  写接口（除 `SetEnabled` / `EStop` 两个 safety-critical 推 v0.5+）。
- 只读 RPC（`ListHardware` / `GetState` / `StreamState` /
  `StreamLogs` 等 6 个）跟 task 流没耦合，留 v0.5+。

### 3.2 备选范围调整

- **(b)** 加 `GetState` / `StreamState`：observability 一并落地。但 S1
  端没 in-process state RPC API；得加 lib API。
- **(c)** 仅 4 个（去 ClearError）：B2 已 lib 落地 `clear_error()`；
  RPC 入口推 v0.5。
- **(d)** 仅 InvokeTask + StreamTaskEvents 2 个最小集：先验 task 提
  交 + 事件流端到端跑通，cancel / status / clear_error 留 B4+。

**默认推进 #2 = (a) 5 个**。如不同意 reviewer 打回 + 给具体范围。

## 4. 进程拓扑 + RR server thread on s1_daemon（**待拍板 #3**）

### 4.1 默认推进：跨进程 + s1_daemon 加 rr_server_thread

跟 A1-3 (1/3) `s0_daemon::rr_server_thread + ipc_thread RR drain`
同款模式，但服务对象是 `Coordinator` API（B2/B3 land）：

- s1_daemon binary 加新线程 `s1_rr_server_thread`，监听 5 个 task
  RPC RR topic：
  * `/<robot_id>/control/task_invoke`
  * `/<robot_id>/control/task_cancel`
  * `/<robot_id>/control/task_status`
  * `/<robot_id>/control/clear_error`

  （**reviewer round 3 同步**：4 个 RR topic 不含 `task_events`；
  events 流走 per-ActionId pubsub `/<robot>/s1/action_events/<action_id>`
  在 §5.2 拍板。round 1/2 残留的 `/control/task_events` RR topic
  已删 —— iceoryx2 RR 是 single-shot，不做 server streaming。）
- 收到 RR request → 转交 coordinator API（in-process）→ 回填
  response → ack 给 gateway。
- 执行**不**碰 RT 路径；coordinator API 是普通锁住的内部状态机
  调用，符合 §4.9 RT 铁律（s1 整套都是非 RT，`run_action_tick_loop`
  跑在普通线程）。

### 4.2 备选

- **(b)** 单 binary 合并 gateway + s1_daemon：跨进程隔离丢失（design
  §5.5 反对："独立进程，崩了不影响机器人运行"）。
- **(c)** gateway → s0 → s1 中转：s0 不该知道 task 语义；架构倒置。

**默认推进 #3 = (a) 跨进程 + 加 rr_server_thread**。

## 5. ActionEvent 流跨进程拓扑（**待拍板 #4**）

### 5.1 关键事实（reviewer round 2 阻断 1）

B2 (1/3) lib 落地的 `ActionTicket`：

```rust
pub struct ActionTicket {
    pub action_id: ActionId,
    pub events: std::sync::mpsc::Receiver<ActionEvent>,  // ← sync, in-process
}
```

`ActionTicket.events` 的 `Sender` 端**仅**存在 `s1_daemon` 进程内
（`Coordinator::CurrentAction.events_tx`），跟 `Receiver` 端配对。
gateway 跨进程**拿不到**这个 `Receiver` —— sync↔async 桥接放
"gateway 端"的 round 1 描述自相矛盾，这是 reviewer round 2 阻断 1
触发的根因。

### 5.2 round 2 拍板拓扑（默认推进）

**两段式跨进程桥接**（s1 端 sync→pubsub；gateway 端 pubsub→async）：

```
s1_daemon process                        gateway process
─────────────────                        ───────────────

Coordinator::submit
  → CurrentAction.events_tx

  ↓ ActionEvent (in-process mpsc)

events_drain_thread                      events_subscribe_thread
  - 持 ActionTicket.events                 - 订阅 iceoryx2 pubsub:
    Receiver (移交进 s1)                     /<robot>/s1/action_events/<action_id>
  - loop recv() →                          - poll latest sample
    encode action_event.fbs body
  - publish to iceoryx2 pubsub:
    /<robot>/s1/action_events/<action_id>
                                            ↓ ActionEvent (decoded)

                                          adapter_to_async_thread
                                            - tokio::sync::mpsc::Sender
                                            - tonic stream forwards
```

**关键决策**：
1. **s1 端不 link tokio**（保 §4.9 + B2 outline §10 决策 #1）。
   `events_drain_thread` 是普通 `std::thread`，跟 `s1_rr_server_thread`
   同款 sync 线程。
2. **gateway 端做 sync→async 桥接**（沿 A1 `rr_io_thread` 模式）。
3. **per-ActionId 独立 pubsub topic**（动态创建 / 销毁）：iceoryx2
   pubsub keep-last 单 slot；每个 ticket 一个独立 topic 让事件流不
   互相覆盖。topic 名 = `/<robot>/s1/action_events/<action_id_hex>`。
4. **InvokeTask RR response 返 `ActionId`**；client 从 ActionId 推
   出 stream topic 名，发起 `StreamTaskEvents` RPC；gateway 根据
   ActionId 订阅 s1 端动态 pubsub topic。

### 5.3 备选模式（reviewer 拍板时可考虑）

| 选项 | 路径 | 优劣 |
|---|---|---|
| **(a) per-ActionId pubsub topic + 双段桥接**（默认推进） | s1 drain thread → pubsub → gateway sub → adapter → tokio | 跟 A1 `rr_io_thread` 同款 sync↔async 模式；s1 端不 link tokio；topic 动态创建/销毁是 iceoryx2 已有能力 |
| (b) 共享 events pubsub topic + ActionId filter | s1 publish 全部 events 到 `/<robot>/s1/action_events/all`；gateway 收后按 envelope.action_id 过滤 | broadcast 浪费 + 不同 client 可能漏帧；多 action 并发时 keep-last 单 slot 互相覆盖严重（B2 单 action 序列化下不漏，但 B3+ scheduler 并发时炸） |
| (c) iceoryx2 RR multi-response | s1 RR server 一次 request 返 N 个 response（如 iceoryx2 支持） | 需查 iceoryx2 0.8.1 是否原生支持；目前 A1 用的是 single-shot RR |
| (d) s1 link tokio 直接 host gRPC stream | s1 端跑 tonic server | s1 link tokio（**违反** B2 outline §10 + §4.9 RT 铁律精神） |

**默认推进 #4 = (a) per-ActionId pubsub topic + 双段桥接**。

### 5.4 RR vs pubsub 分工（**待拍板 #4a**）

- **RR 用于**：`InvokeTask` / `CancelTask` / `GetTaskStatus` /
  `ClearError`（single-shot request-response，沿 A1 ClearEStop 模
  式）。
- **pubsub 用于**：`StreamTaskEvents` 的 events 流（per-ActionId
  topic 动态注册）。

**待拍板**：iceoryx2 0.8.1 动态创建/销毁 pubsub service 的开销 +
service 名命名空间冲突防护（如 ActionId 碰撞 / leftover topic
未清理）。本 outline 标"需运行期评估"，B4 (1/3) impl 时再回填具
体性能数据。

### 5.5 backpressure / cancel / lifecycle 语义（reviewer round 3 阻断 2 修）

round 1/2 残留按"ticket holder 在 gateway 端"旧模型描述 cancel；
round 2 拓扑下 `ActionTicket.events` Receiver 在 s1
`events_drain_thread` 内（**不**在 gateway），gateway drop tonic
stream **不会** drop Receiver。本节按新拓扑（s1 sender / pubsub /
gateway sub）重写四个生命周期点。

**1. backpressure（gateway 端）**：

iceoryx2 pubsub keep-last 单 slot；s1 publish 速率快时 gateway sub
来不及拉走会丢中间帧（最新 wins）。adapter thread `tokio::sync::mpsc::Sender::try_send`
满了 → drop event + `tracing::warn!`（一致性 by 客户端自己 catch up
`GetTaskStatus` 拿当前快照）。

**默认推进**：drop + warn；不 block。

**2. s1 `events_drain_thread` 终止条件**：

s1 端 `events_drain_thread` 持 `ActionTicket.events: Receiver<ActionEvent>`。
Receiver `recv()` 返 `Err(RecvError)` = sender drop（=
`Coordinator::CurrentAction` 被 drop = 终态/ShuttingDown 已写入 ring
+ current = None）。drain thread 此时 break loop → 触发 topic
cleanup（详 #4）→ thread 退出。

**默认推进**：drain thread = 1 thread per ActionTicket；coord submit
成功后 spawn；recv 返 Err 时 break + cleanup + join。

**3. gateway client tonic stream Drop（client disconnect）**：

tonic server-streaming 在 client 断开时 drop response stream → gateway
adapter thread 检测到 `tokio::sync::mpsc::Sender` 的 receiver 被 drop
（`send` 返 Err）→ adapter thread break → unsubscribe iceoryx2
pubsub topic（drop subscriber handle）→ gateway side cleanup 完成。

**关键决策**：gateway disconnect **不**通知 s1 释放 ticket。s1 端
`ActionTicket` 保留在 `Coordinator::CurrentAction` 直到 backend 自然
完成 / cancel / fail。用户要主动停 task → 调 `CancelTask` RPC（明确
意图，跟 stream Drop 区分）。

**理由**：避免 client 短暂断网误触发 task 取消；stream 是 audit
通道，不是控制通道（控制走 `CancelTask`）。

**4. per-ActionId pubsub topic cleanup**：

每个 ActionTicket 一个独立 topic `/<robot>/s1/action_events/<action_id>`
（动态创建）。终态后 topic 应删除避免 leftover：

- s1 `events_drain_thread` recv 到 terminal event（Completed /
  Failed / Cancelled）→ publish + sleep 短窗口（让 gateway sub
  catch up）→ unregister iceoryx2 pubsub service → thread 退出。
- 短窗口默认 100 ms（待拍板 #4b：iceoryx2 keep-last + reader catch-up
  延迟实测后回填）。
- gateway sub 端检测 service 消失 → adapter thread 自然 break
  （iceoryx2 sub on dead service 行为待确认 / B4 (1/3) impl 时验证）。

**默认推进**：terminal event 后 100 ms drop service；如 reviewer
倾向更长 / 更短 / 不 cleanup（让 OS 进程退出时回收）则 round 4 修。

### 5.6 待拍板 #4b（lifecycle / cleanup 细节）

- topic cleanup grace window 默认 100 ms 是否合适？
- gateway sub 端 service 消失检测语义（iceoryx2 0.8.1 行为待 impl
  验证）。
- 进程崩溃时 leftover topic 怎么清理？（systemd restart hook /
  startup sweep / 都不做让 daemon 启动期重新分配 service name？）

## 6. proto schema vs 跨进程 fbs schema（**待拍板 #5**）

### 6.1 A1 现状（reviewer round 2 阻断 2 修正）

round 1 outline 误写"A1 用 prost message 包 FlatBuffers payload
bytes（`message ClearEStopRequest { bytes payload = 1; }`）"。**实际
A1 不是这个形态**，是 typed prost message + 内部独立 fbs RR body：

| 层 | A1 实际 | 用途 |
|---|---|---|
| **外部 tonic / gRPC** | typed prost `ClearEStopCommand { meta, confirmation }` / `Ack { request_id, cleared_at_ns, dry_run, ... }`（`crates/robot-rpc/proto/robot_control.proto`） | 客户端 ↔ gateway 跨网络；schema frozen，仅 append |
| **gateway → daemon RR** | gateway 把 typed prost 解构 + 自构造 fbs body（`crates/robot-msg/schemas/clear_estop.fbs::ClearEStopRequest`）+ envelope，通过 iceoryx2 RR 发给 s0_daemon `rr_server_thread` | 跨进程 wire；fbs schema 在 `robot-msg` 注册 |

**关键观察**：A1 的 proto / fbs 是**两套独立 schema**，不是 wrapper。
gateway 内做 proto ↔ fbs 转换（typed Rust struct 中转）。

### 6.2 B4 schema 计划（拆 typed proto vs fbs RR body）

**外部 tonic proto**（B4 加进 `crates/robot-rpc/proto/robot_control.proto`）：

```proto
service RobotControl {
    rpc ClearEStop       (ClearEStopCommand) returns (Ack);                   // A1 land
    rpc InvokeTask       (InvokeTaskCommand) returns (TaskHandle);            // B4 加
    rpc CancelTask       (CancelTaskCommand) returns (Ack);                   // B4 加
    rpc GetTaskStatus    (TaskHandleRef)     returns (TaskStatus);            // B4 加
    rpc StreamTaskEvents (TaskHandleRef)     returns (stream TaskEvent);      // B4 加
    rpc ClearError       (ClearErrorCommand) returns (Ack);                   // B4 加
}

message InvokeTaskCommand {
    CommandMeta meta             = 1;
    ActionKindProto kind         = 2;   // typed enum（reviewer round 2 默认 #5a 已锁，详 §6.3）
    uint64      deadline_ns      = 3;
    uint32      priority         = 4;
    uint32      payload_schema_id = 5;
    bytes       payload          = 6;   // fbs payload；schema_id 路由
}
message TaskHandle      { string request_id = 1; bytes action_id = 2; }
message TaskHandleRef   { string request_id = 1; bytes action_id = 2; }
message CancelTaskCommand { CommandMeta meta = 1; bytes action_id = 2; }
message ClearErrorCommand { CommandMeta meta = 1; }
message TaskStatus      { ... 详 §6.4 待拍板字段集 }
message TaskEvent       { ... 同上 }
```

**内部 fbs RR body**（B4 加进 `crates/robot-msg/schemas/`）：

```
schemas/action_request.fbs       —— gateway → s1 RR call body for InvokeTask
schemas/action_status.fbs        —— s1 → gateway RR response body for GetTaskStatus
schemas/action_event.fbs         —— s1 → gateway pubsub body for events stream（详 §5.2）
```

**这两套 schema 必须分开维护**：tonic proto 是对客户端的 API 边
界（HTTP/2 wire），fbs 是 daemon 间 iceoryx2 内部 wire（共享内存 zero-
copy）。两者**不**能合并成一套（A1 已建立此分工）。

### 6.3 prost vs fbs 字段对应（待拍板 #5）

每个 typed proto 字段如何映射到 fbs body：

- `InvokeTaskCommand.kind`（proto `ActionKindProto` typed enum） →
  `action_request.fbs::kind`（fbs enum 同款 variant 集；保 proto / fbs
  / Rust ActionKind 三层 variant 一一对应）。
- `InvokeTaskCommand.payload`（proto bytes） → `action_request.fbs::payload`
  （fbs `[ubyte]`；payload 内容由 `payload_schema_id` 决定，B4 mock_dwell
  / hold_pose 都用空 payload）。

**待拍板 #5a**：proto `kind` 用 string 还是 typed enum？
- string：跟 ActionKind enum doc 描述一致；好扩展，但客户端容易拼错。
- typed enum：`enum ActionKindProto { DWELL_MS = 0; HOLD_POSE = 1; }`；
  类型安全，但每加新 ActionKind 同步改 proto + lib。

**默认推进 #5a = typed enum**，proto / lib 同步扩 + 跨进程 fbs 也用
对应 fbs enum。客户端误传值靠 protobuf decode 拒绝。

### 6.4 fbs body 字段集草案（待拍板 #5b）

### 6.2 需要的 fbs schema

- **`action_request.fbs`**：`{ action_id, kind (fbs enum 同
  ActionKind), deadline_ns, priority, payload_schema_id, payload (bytes),
  idempotency_key, source_actor }` —— gateway InvokeTask handler 解
  proto → 构造此 fbs body → 发 RR 给 s1。
- **`action_event.fbs`**：`{ at_ns, kind (fbs enum: Started /

  此 body publish 到 per-ActionId pubsub topic。

  Completed / Failed / Cancelled), progress (option f32), outcome
  / failure 字段 }` —— s1 RR `GetTaskStatus` response body。

按 [`docs/CHANGELOG.md`](../CHANGELOG.md) 同款"schema frozen，仅
append"机制：fbs 字段定义后不动；新需求加 field append。tonic proto
schema 同款（A1-1 (3/3) 已建立的 frozen 约定）。

## 8. AuthContext + IdempotencyCache（**待拍板 #7**）

### 8.1 复用 A1 模式

- AuthContext：fake token + role 模式（A1-1 落地）；B4 5 个 RPC 各
  自声明所需 role：
  * `InvokeTask`：复用 A1 `Capability::InvokeTask`（已 enum 占位，A1
    没真用过）。**`operator+`**（rpc_roles.toml 现状 operator /
    maintainer / admin 都拿 invoke_task）。
  * `CancelTask` / `GetTaskStatus` / `StreamTaskEvents`：A1
    `Capability` enum **没**这 3 个 variant（详 reviewer round 2 阻断
    4）。`Capability` 当前仅 `ReadState / InvokeTask / SetEnabled /
    ClearError / ClearEStop / EStop / ReloadCalibration / SetPolicy /
    Shutdown` 9 个。

    **待拍板 #7a 修法两选**：
    - **(a) 复用现有 capability 不扩 enum**：CancelTask / Status /
      Stream 都视为"任务执行权限的延伸"，复用 `InvokeTask`
      capability；`GetTaskStatus` / `StreamTaskEvents` 也可考虑复用
      `ReadState`（更窄 = `viewer` 也能查任务进度）。
    - **(b) 扩 capability enum**：加 `CancelTask` / `GetTaskStatus`
      / `StreamTaskEvents` 3 个新 variant + 同步 `as_str` /
      `from_str` + `configs/rpc_roles.toml` 4 个 role 表全部加 + lib
      unit 测试覆盖。

    **默认推进 #7a = (a)** —— InvokeTask / CancelTask 用
    `Capability::InvokeTask`（同 task lifecycle 写权限）；
    GetTaskStatus / StreamTaskEvents 用 `Capability::ReadState`
    （只读，viewer+ 都能用）。简化 capability 表 + 不动 A1 已 land
    的 enum；如 reviewer 倾向 (b) 则 round 3 修。
  * `ClearError`：**`maintainer+`**（错误恢复权限）。

    **reviewer round 2 阻断 4 子项**：当前 `configs/rpc_roles.toml`
    `[roles.operator]` 含 `clear_error`；改成 `maintainer+` = **角色
    表收紧变更**。修 `[roles.operator]` 删 `clear_error`；
    `[roles.maintainer]` / `[roles.admin]` 保留。这条变更必须明示是
    收紧（不是 capability 扩展），并跟 `[roles.viewer]` 不动 /
    `[roles.operator]` 删 / `[roles.maintainer+]` 保留 一起 land 到
    B4 (1/3) commit。**待拍板 #7c**：reviewer 接受这条收紧吗？
- **IdempotencyCache**（reviewer round 2 阻断 3 修正）：A1 已建模
  `IdempotencyCache::with_capacity` + `idempotency_key`-key TTL 缓
  存；但 cache 值是 ClearEStop 专用 `CachedAck { cleared_at_ns:
  u64, dry_run: bool }`（详 `crates/robot-rpc/src/idempotency.rs::CachedAck`），
  cache key 也只是 `idempotency_key` 字串，**没 method namespace**。

    **B4 5 个 RPC 直接复用 A1 cache** 不能成立 ——
    `InvokeTask` / `CancelTask` / `GetTaskStatus` / `ClearError` 各
    自的 ack payload 不同（如 `InvokeTask` 返 `TaskHandle`，`ClearError`
    返简单 `Ack`）；同款 `idempotency_key` 在不同 RPC 上调用应是
    **独立** cache miss，不能跨 RPC 命中。

    **待拍板 #7b 修法三选**：
    - **(a) 每 RPC typed cache**：每个 RPC 一个独立
      `IdempotencyCache<T>`（如 `IdempotencyCache<TaskHandleAck>` /
      `IdempotencyCache<ClearErrorAck>`）。lib 改动 = `CachedAck` 改
      泛型 + 5 个 cache 实例。
    - **(b) cache key 加 method namespace**：保 `CachedAck` 单类型，
      cache key 改成 `(method_name, idempotency_key)` tuple 或
      `format!("{method}:{key}")`；cache 值用 enum
      `CachedResponse { ClearEStop(...), Task(TaskHandle), ... }`。
      lib 改动 = `CachedAck` 改 enum + key 加 method 前缀 + A1
      ClearEStop 路径同步迁移到新 enum variant。
    - **(c) generic response cache**：`CachedAck` 改成 `bytes`
      payload + method namespace key；handler 各自 encode / decode。
      最 generic 但 handler 多一层序列化 overhead。

    **默认推进 #7b = (b)** —— 单 cache 实例 + `CachedResponse`
    enum + method 前缀 key。最少 lib churn + A1 路径迁移成本可控
    （ClearEStop 一处）。如 reviewer 倾向 (a) typed-per-RPC 则 round
    3 修。

    **拒方案**：~~"共享一个 cache（A1 同款）"~~（round 1 默认推进，
    round 2 阻断 3 打回 —— A1 cache 是 typed ClearEStop-only，跨
    RPC 复用会 cache 命中错位 ack）。

### 8.2 dry_run

A1 ClearEStop 已建模 `meta.dry_run = true` 跳过实际 fsync + state

**默认推进**：B4 不做 dry_run（task 路径无 fsync；submit 失败影响

## 10. wire 契约保持（来自 B3 §3.7）

B3 落地的硬约束：**HoldPose backend 产 body 的 `source_task_id` ==
run_action_tick_loop 当前 `TickState.cmd_seq`；S0 ipc_thread 把

  `FrameHeader.seq`。
- gateway 端把 RPC `request_id` 当 `ActionId`（B2 outline §2.1
  锁定）；不影响 `source_task_id`（不同字段、不同语义）。

  in-process API；body bytes 仍由 backend / hold loop 产，gateway
  不参与 body 字节构造。

如未来加 RT emergency / pre-empt action（v0.4+），仍必须保 cmd_seq
单调；emergency body 的 source_task_id 必须从 `TickState.cmd_seq`
取，不得新建私有 counter（详 [`v0.3_b3_summary.md`](v0.3_b3_summary.md)
§3.7）。

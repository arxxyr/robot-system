## 1. B4 范围 / 不在范围

### 1.1 在范围

- **`robot-rpc` gateway 扩 RPC 子集**（5 个 method 默认推进，详 §3
  待拍板 #2）：
  * `InvokeTask`：客户端提交 action → gateway 转 RR call → s1_daemon
    coordinator.submit → 返 `TaskHandle = ActionId`。
  * `CancelTask`：客户端取消 action → gateway 转 RR call →
    coordinator.cancel。
  * `GetTaskStatus`：客户端查询单个 action 状态 → coordinator.status。
  * `StreamTaskEvents`：server-streaming → gateway adapter thread
    把 `ActionTicket.events: std::sync::mpsc::Receiver<ActionEvent>`
    桥到 `tokio::sync::mpsc::Sender<ActionEvent>` → tonic stream
    response。
  * `ClearError`：清 coordinator `Degraded` 状态（B2 outline §10 决
    策 #5 锁定 RPC 入口）。
- **进程拓扑**（详 §4 待拍板 #3）：
  默认推进 = `robot_rpc_gateway` 跟 `s1_daemon` 跨进程，复用 A1-3
  (1/3) `rr_server_thread` 模式 —— `s1_daemon` 加 RR server thread
  接 5 个 task RPC 的 RR 路径。**不**合并 gateway + s1_daemon 进程
  （设计文档 §5.5 锁定独立进程）。
- **新加 fbs schema**（B2 outline §10 决策 #9 推 B4 的时点）：
  `action_request.fbs` / `action_status.fbs` / `action_event.fbs` 跨
  进程消息格式。具体字段集详 §6 待拍板 #5。
- **adapter thread 模式**（详 §5 待拍板 #4）：默认 sync↔async 桥接
  跟 A1-3 (2/3-b2-1) `rr_io_thread` 同款模式 —— gateway 进程内一
  个 `std::thread` 持 `mpsc::Receiver<ActionEvent>`，loop 调
  `try_recv` / `recv` → `tokio_sender.try_send`，把同步事件转成
  async stream 项。
- **错误码映射**（详 §7 待拍板 #6）：`SubmitError` /
  `ActionCancelError` / `ClearError` → tonic `Status` / `Code` 的
  映射表。
- **AuthContext + IdempotencyCache**（详 §8 待拍板 #7）：复用 A1 已
  建模的 fake token 路径 + `IdempotencyCache::with_capacity` 模式；
  v0.1.2 不引 mTLS / OIDC（推 v0.5+）。
- **测试计划**（详 §11）：lib unit + 跨进程 integration test
  （`crates/robot-rpc/tests/...` 沿 A1 模式）+ 双路
  `crash_restart_smoke` 5/5+5/5 wiring 回归门槛（沿 B3 同款）。

- **§5.3 全 12 RPC 一次到位**：B4 仅 5 个 task / clear 方法（详

## 3. RPC method 选择（**待拍板 #2**）

### 3.1 默认推进 5 个

| RPC | 来源 | 用途 |
|---|---|---|
| `InvokeTask` | design §5.3 | 提交 action → 返 `TaskHandle = ActionId` |
| `CancelTask` | design §5.3 | 取消 action |
| `GetTaskStatus` | design §5.3 | 查询单个 action 当前状态 |
| `StreamTaskEvents` | design §5.3 | 订阅 action 事件流（server streaming） |
| `ClearError` | design §5.3 | 清 coordinator `Degraded` 状态 |

理由：
- 这 5 个直接对应 B2 (2/3) `Coordinator::{submit, cancel, status,
  clear_error}` 4 API + B2 (1/3) `ActionTicket.events` 接口。lib
  side **已埋好**接口；B4 仅做 RPC wiring。
- `ClearEStop`（A1）+ 这 5 个 = `RobotControl` service 的所有控制
  写接口（除 `SetEnabled` / `EStop` 两个 safety-critical 推 v0.5+）。
- 只读 RPC（`ListHardware` / `GetState` / `StreamState` /
  `StreamLogs` 等 6 个）跟 task 流没耦合，留 v0.5+。

### 3.2 备选范围调整

- **(b)** 加 `GetState` / `StreamState`：observability 一并落地。但 S1
  端没 in-process state RPC API；得加 lib API。
- **(c)** 仅 4 个（去 ClearError）：B2 已 lib 落地 `clear_error()`；
  RPC 入口推 v0.5。
- **(d)** 仅 InvokeTask + StreamTaskEvents 2 个最小集：先验 task 提
  交 + 事件流端到端跑通，cancel / status / clear_error 留 B4+。

**默认推进 #2 = (a) 5 个**。如不同意 reviewer 打回 + 给具体范围。

## 4. 进程拓扑 + RR server thread on s1_daemon（**待拍板 #3**）

### 4.1 默认推进：跨进程 + s1_daemon 加 rr_server_thread

跟 A1-3 (1/3) `s0_daemon::rr_server_thread + ipc_thread RR drain`
同款模式，但服务对象是 `Coordinator` API（B2/B3 land）：

- s1_daemon binary 加新线程 `s1_rr_server_thread`，监听 5 个 task
  RPC RR topic：
  * `/<robot_id>/control/task_invoke`
  * `/<robot_id>/control/task_cancel`
  * `/<robot_id>/control/task_status`
  * `/<robot_id>/control/task_events`（server streaming → response
    stream，**待拍板 #4**）
  * `/<robot_id>/control/clear_error`
- 收到 RR request → 转交 coordinator API（in-process）→ 回填
  response → ack 给 gateway。
- 执行**不**碰 RT 路径；coordinator API 是普通锁住的内部状态机
  调用，符合 §4.9 RT 铁律（s1 整套都是非 RT，`run_action_tick_loop`
  跑在普通线程）。

### 4.2 备选

- **(b)** 单 binary 合并 gateway + s1_daemon：跨进程隔离丢失（design
  §5.5 反对："独立进程，崩了不影响机器人运行"）。
- **(c)** gateway → s0 → s1 中转：s0 不该知道 task 语义；架构倒置。

**默认推进 #3 = (a) 跨进程 + 加 rr_server_thread**。

## 5. sync↔async adapter thread 模式（**待拍板 #4**）

### 5.1 ActionEvent 流的桥接路径

B2 (1/3) lib 落地的 `ActionTicket`：

```rust
pub struct ActionTicket {
    pub action_id: ActionId,
    pub events: std::sync::mpsc::Receiver<ActionEvent>,  // ← sync
}
```

跨 sync↔async 边界（`std::sync::mpsc::Receiver` → `tokio::sync::mpsc::Sender`）
的桥接放**哪一端**：

| 选项 | 路径 | 优劣 |
|---|---|---|
| **(a) gateway 端桥接**（默认推进） | s1 起 RR server stream，gateway 收 RR response stream → adapter thread → tokio sender → tonic stream | 跟 A1 `rr_io_thread` 同款模式；s1 端不 link tokio |
| (b) s1 端桥接 | s1 起 tokio runtime + adapter thread；通过 RR 把 ActionEvent 序列化发出 | s1 link tokio（违反 §4.9 + §10 决策） |
| (c) 中转 stream pubsub topic | s1 publish ActionEvent 到 pubsub topic；gateway 订阅 + filter by ActionId | 简单但每个 ticket 有自己的 channel，pubsub broadcast 浪费 + ActionId filter S0 也要解 |

**默认推进 #4 = (a)**。adapter thread 跑在 gateway 进程内，复用
A1-3 (2/3-b2-1) `rr_io_thread` 模式（gateway 持 tokio runtime；s1
完全同步）。

### 5.2 RR stream 形态（**待拍板 #4a**）

iceoryx2 RR 是单次请求-响应；server streaming（一个 request → N 个
event response）需要：

- **(i)** RR request_id → multi-response 模式（iceoryx2 内置支持？需
  查）。
- **(ii)** RR 单次响应 = "stream channel 句柄"，client 之后通过 pubsub
  + topic name (含 ActionId) 订阅 events。
- **(iii)** 每个 ActionTicket 一个独立的 iceoryx2 stream service +
  动态创建 / 销毁。

**默认推进 #4a = (ii)** 简单 + 复用既有 pubsub 机制。**待拍板**：
是否需要 (i) (iii) 评估。

### 5.3 backpressure / cancel 语义

- **backpressure**：tonic client 慢消费时 server-side stream 会 block。
  gateway adapter thread 用 `try_send` + 满了就 drop event（log
  warning）还是 block？
- **cancel**：client tonic streaming 断开时 stream Drop；adapter
  thread 应停止 forwarding events，并通知 s1 端释放 ticket（或不释
  放，让 ticket 自然消亡）。

**默认推进**：
- backpressure：drop + warn（`tracing::warn!`）。一致性 by 客户端
  自己 catch up（`GetTaskStatus` 可补）。
- cancel：tonic stream drop → adapter thread 自动结束循环；s1 端
  ticket 留在原 coordinator，自然完成生命周期（ticket holder 在
  gateway 端，drop receiver 后 send 失败 swallow，详 B2 (2/3)
  `ActionTicket` doc）。

## 7. 错误码映射（**待拍板 #6**）

### 7.1 SubmitError → tonic Status

| `SubmitError` variant | tonic `Code` | rationale |
|---|---|---|
| `InvalidRequest(msg)` | `InvalidArgument` | 客户端字段错 |

## 10. wire 契约保持（来自 B3 §3.7）

B3 落地的硬约束：**HoldPose backend 产 body 的 `source_task_id` ==
run_action_tick_loop 当前 `TickState.cmd_seq`；S0 ipc_thread 把
`fb.source_task_id()` 写成 `JointCommandBuf.seq`；adapter.rs 要求
单调递增（`rt_thread` 判 `CONTROL_LOST` → `ACTIVE` 用）**。

B4 **不**得破坏：
- gateway adapter thread 仅消费 `ActionEvent` 流；**不**碰
  `JointCommand.source_task_id`。
- gateway adapter thread 仅消费 `ActionEvent` 流；**不**碰
  `FrameHeader.seq`。
- gateway 端把 RPC `request_id` 当 `ActionId`（B2 outline §2.1
  锁定）；不影响 `source_task_id`（不同字段、不同语义）。
- s1_daemon `rr_server_thread` 处理 RR call 时仅调用 coordinator
  in-process API；body bytes 仍由 backend / hold loop 产，gateway
  不参与 body 字节构造。

如未来加 RT emergency / pre-empt action（v0.4+），仍必须保 cmd_seq
单调；emergency body 的 source_task_id 必须从 `TickState.cmd_seq`
取，不得新建私有 counter（详 [`v0.3_b3_summary.md`](v0.3_b3_summary.md)
§3.7）。

**待拍板**：是否需要本契约升级为 §6.7 第 6 条 invariant？
**默认推进 #9**：保持现状（CHANGELOG 已记 + summary §3 已审计；
proto / errata 不动）；除非 B4 实际跨段 wiring 难度暴露 corner case。

# Deployment Targets（部署目标）

本目录汇总 `robot-system` 规划支持的具体机器人平台，以及每个平台上游（已有参考实现）的现状分析 + 迁移映射。

目的是让 framework（`robot-s0` / `robot-s1` / `robot-transport` / …）在设计和演进时**始终针对真实部署目标的硬约束**，而不是抽象出一个"通用框架"却没人跑得起来。

## 优先级

| 平台 | 上游参考 | 框架阶段 | 状态 | 文档 |
|------|---------|---------|------|------|
| XLeRobot | `dimos`（Python） | v0.4（首个 adapter 落地目标） | 规划中 | 见 `00_design.md` §11.3 |
| ATOM01 人形 | `atom01_deploy`（ROS 2 + C++） | v0.5 候选（端到端 RL 推理） | 规划中 | [`atom01.md`](atom01.md) |
| AgileX Piper | — | v0.6（异构验证） | 规划中 | 见 `00_design.md` §11.4 |
| 移动底盘 / 四足 / 其他人形 | — | ≥ v0.7 | 未立项 | — |

## 文档约定

每个 `targets/<name>.md` 至少包含：

1. **硬件清单** —— 控制器 / 传感器 / 执行器 / 总线
2. **上游参考现状** —— 已有实现的关键算法、配置、不变量（可精确复刻到 Rust 侧）
3. **在 robot-system 中的映射** —— 哪些走 S0 / 哪些走 S1 / 哪些走 policy host / 哪些是业务层 app crate
4. **新增的 adapter 需求** —— crate 边界、trait 实现范围、RT 约束下要注意的点
5. **风险与门槛** —— 精度、延迟、复现性、RT 违例、训练-部署契约
6. **实施顺序** —— 不引入新的 `v0.x` 顺序，只描述"在该版本就位后"这台机器人还差哪些工作

> **不要**把部署目标写入 `00_design.md` —— 设计冻结，目标文档只是**对齐 reality 的参考资料**，可以随上游项目演进更新。
